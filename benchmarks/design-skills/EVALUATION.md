# Blind evaluation rubric

Review candidates only as `A`, `B` and `C`. Do not reveal or infer which skill produced which candidate until the written comparison is complete.

Use `strong`, `mixed` or `weak` for each lens and cite visible or observed evidence.

| Lens | What to inspect |
| --- | --- |
| Core-flow clarity | Can a first-time viewer complete ready → active → loss → fallback → recovery → arrival without narration? |
| Failure and trust | Does signal loss clearly distinguish known, pending, simulated and recoverable behaviour without implying surveillance or emergency protection? |
| Visual hierarchy | Is the next meaningful action obvious at both viewports, with deliberate type, spacing, contrast and composition? |
| Distinctiveness | Is there a coherent, memorable Relay-specific signature rather than generic AI/SaaS styling? |
| Responsive craft | Does the design preserve hierarchy, controls and intentional composition at 1440 × 1000 and 390 × 844? |
| Accessibility | Are semantics, keyboard focus, live feedback, target sizes, contrast and reduced motion handled credibly? |
| Purposeful motion | Does motion clarify state or continuity, and does the interface remain good when motion is reduced? |
| Implementation truth | Do all required controls work offline, and are simulations labelled honestly? |
| Restraint | Did the candidate resist feature invention, decorative clutter and component/card sprawl? |

## Decision rule

Prefer the candidate with the strongest complete product argument, not the one with the most decoration. A candidate cannot win if the required path fails, content is clipped, keyboard operation breaks, or the demo claims real functionality it does not have.

Record:

- strongest characteristic
- weakest characteristic
- observed defects
- which human edits would still be required
- pairwise preference and why
- provisional winner
- confidence and the smallest additional test that could reverse the decision
